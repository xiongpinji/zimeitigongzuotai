# R1 四平台安全账号离线桌面测试（2026-09-28）

按“先测试、不打包”要求，在 Windows 源码构建 `66e128d` 上执行 `node app/scripts/smoke-secure-accounts-win.cjs`，退出码 0。脚本使用 Git 忽略目录中的独立 Electron `userData`，经真实设置页 UI 为抖音、快手、视频号、小红书各创建两个**仅有虚构备注的账号元数据**。每个平台的两条记录同名，但拥有不同 UUID 和归属人。全程未点击登录、会话检查或发布。

首次关闭并重启应用后，安全账号页和 `accountV2API.list()` 均返回原有 8 条记录，UUID、平台、归属人、未知状态、无会话状态一致。按第一条抖音账号的 UUID 在界面删除后，其余 7 条保留；再次关闭并重启，7 条仍在。独立用户目录的 `publish-v2/registry.json` 存在、`sessions/` 为空。旧“发布账号”页显示 0 条记录及“仍使用旧账号体系”的提示，说明新安全账号尚未接入发布链。Renderer 页面异常 0。此外，Electron `safeStorage` 在本机可用，合成字符串加密后将密文保存为文件，应用重启后从文件读回并成功解密；这是加密 API 独立探针，并未模拟平台登录。结果与截图位于被 Git 忽略的 `data/runtime/validation/r1-accounts-1790547356560/`。

同一源码基线的聚焦回归：账号核心、IPC、bootstrap、Renderer store 和设置页 **5/5 文件、153/153 测试通过**。独立负载配置 `vitest.load.config.ts` 的 `account-vault.load.ts` **1/1 通过**：测试用编码器与假平台为 100 个虚构账号（四平台各 25 个）顺序写入会话，假探针标记 99 有效、1 过期，新进程重开后仍隔离，临时明文目录 0。该负载用例不是并发发布或真实平台容量证明。

本轮证明的是四平台**账号元数据**在隔离桌面用户目录内可创建、重启保留并按 UUID 删除，以及 Electron 加密 API 可对合成数据跨重启解密。未验证 `account-v2` 保存真实平台会话后的跨重启解密、用户授权账号的扫码首登/续登、A 账号过期时 B 账号的真实会话保持，也未验证新账号参与批量发布。因此 [R1 产品验收](../roadmap-and-acceptance.md)仍未关闭。后续应先完成安全账号到发布工作台的接线，再在用户授权的试点范围内做真实平台验收；当前不触碰真实账号或平台。
