# R2 预览与导出逐帧比对：门槛未通过（2026-09-28）

用户要求先测试、暂不打包。本轮在 Windows 源码 Electron 上，以主库 `6ab6096` 为测试基线，使用 Node v24.17.0 和隔离的合成工程复测。`npx electron-vite build` 退出码 0，复测在该次源码构建之后进行。没有打包、接入真实账号、读取真实录屏或向平台发布。隔离输入为 15 fps 的 3 秒 `testsrc2` 视频和 3 秒纯蓝视频，工程时间线为 30 fps；测试数据和运行输出都位于 Git 忽略的 `data/runtime/validation/`。

`app/scripts/smoke-editor-multitrack-win.cjs` 现记录预览滑块的**实际**时间、媒体元素时间和时间线帧号，再用 FFmpeg `select=eq(n\,frameIndex)` 提取对应导出帧，避免按 `-ss` 秒数抽帧时跳到邻帧。本轮重新运行该源码 UI smoke：素材扫描、双轨放置、分割、撤销/重做、保存重开、MP4 导出和完整解码均通过；工程有 2 条视觉轨、3 个片段，导出 H.264 1280×720 + AAC，5.461333 秒，页面异常 0。预览抽样点为时间线第 42 帧（1400 ms）和第 90 帧（3000 ms）。这项 smoke 的“通过”只证明上述工作流，不代表严格画面一致。

新增 `app/scripts/check-editor-preview-export-parity-win.cjs` 作为严格比对门槛。它从同一个隔离工程重新打开实际桌面 UI，在时间线第 42、43、90 帧暂停截图，按帧号提取导出图，裁去舞台边框后把导出图缩至相同尺寸计算 SSIM。为排除本机 Chromium 截图的 ICC 和 GPU 视频合成差异，比较进程仅在测试时使用 `--disable-gpu --force-color-profile=srgb`；产品默认启动参数没有改。门槛设置为 SSIM ≥ 0.92，当前**退出码 1**：

作为比对方法的同帧控制，把第 43 帧的预览图与导出第 42 帧（两者素材时间码都为 0.733 s）比较，SSIM 为 0.949360；因此上表的两项失败不能仅归因于缩放或 H.264 压缩。预览第 42 帧媒体元素 `currentTime=0.733333`，实际可见仍是源帧 10；第 43 帧 `currentTime=0.766666`，可见源帧 11。源码中预览使用 HTML5 `<Video>`，导出使用 `<OffthreadVideo>`；结合 15/30 fps 混用，**推断**两条解码/取帧路径在帧边界采用了不同选择，尚未证明所有帧率或真实素材均如此。该问题使 R2 的严格预览/导出一致门槛继续保持未通过。

另行检查了颜色干扰：默认 Electron 截图中的纯蓝视频中心像素为 RGB `[28,34,246]`，浏览器 Canvas 读取同一源视频中心为 `[0,0,255]`，导出帧为 `[0,0,254]`。强制 sRGB 但保留 GPU 时舞台截图为 `[26,35,255]`；禁用 GPU 且强制 sRGB 时舞台截图为 `[0,0,253]`，导出仍为 `[0,0,254]`。这表明本机截图/合成路径本身会引入颜色差异，不能把早期截图 SSIM 直接当作产品像素偏差；也不能用关闭 GPU 的测试结果证明默认 UI 的颜色完全一致。当前没有以全局关闭 GPU 作为产品修复，因为它可能改变剪辑性能和播放体验。
