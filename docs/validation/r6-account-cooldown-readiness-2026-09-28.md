## 测试门槛与范围

[阶段一验收](../roadmap-and-acceptance.md)要求“出现风险信号自动降并发或停派”。本次具体检查账号级限流：账号 A 的首条任务确认未提交且要求等待 45 秒后，该账号的其他视频也应等待；同平台账号 B 应继续处理。这里的“账号级”是待满足的产品需求，当前 `PublishAttemptOutcome.throttled` 只有 `retryAfterMs`、`errorCode`、`confirmedNotSubmitted` 等字段，**没有限流作用域字段**。不能把这次失败解释成已经违反一个现有、明确声明的账号级接口契约；它揭示了产品验收能力缺口。

新增 `app/scripts/probe-publish-account-cooldown.cjs`，经 esbuild 加载当前 `electron/publish/durable-queue.ts`。使用队列已有的执行器、核对器和时钟注入端口，仍由真实队列代码负责领取、状态迁移、JSON 持久化和重新读取。每例有账号 A 的两条不同视频与账号 B 的一条视频，global/device/per-account 预算均为 1；首条返回模拟限流或未知提交，后续返回合成远端 ID。

四种平台标识为 `douyin`、`kuaishou`、`wechat-channels`、`xiaohongshu`，都经过同一个通用队列实现。每种标识检查同一对象内的限流、重新打开 JSON store 后的限流，以及重新打开后的未知提交对照，共 12 个场景。重新打开指同一 Node 进程创建新队列对象，不是强制进程退出。45 秒由虚拟时钟推进，不是等待 45 秒的真实平台请求。

脚本不加载平台适配器、账号库、浏览器或模型，不读取真实录屏，不登录或发布。所有任务、账号和返回值都是合成数据；证据只写入 Git 忽略的 `data/runtime/validation/`。

## 源码原因与后续验收

`durable-queue.ts` 的 `throttled` 分支只更新当前任务的 `nextAttemptAt`。领取阶段逐条检查这个时间，再检查上传租约/未知提交的账号集合、单轮互斥和静态预算；限流任务已经进入 `retryable_failure`，没有形成账号或平台范围的持久停派状态。测试结果与这个实现路径一致。

后续实现合同需要明确适配器可信返回的限流作用域与恢复条件，再验证账号级停派及其持久化；平台级限流、未到期的手动重试、取消/删除原任务后的等待，以及未知提交守卫兼容性也应独立验收。不能仅凭错误文本推断平台范围，也不能为解除等待把未知提交改成可重发。本轮没有选择实现方案或直接修队列。
